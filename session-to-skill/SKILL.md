# Session to Skill

## Quick start

当用户要求把会话经验沉淀为 skill 时，先判断要沉淀的是当前对话、指定历史文件，还是“当前目录第 N 新”的会话历史。不要直接复制聊天记录；要抽象成可复用触发条件、流程、检查清单和模板。

最小流程：

1. 定位材料：当前会话靠上下文；历史会话用 `find`/时间排序定位 `.jsonl`。
2. 提炼模式：找出用户目标、关键决策、成功反馈环、失败/中断、最终交付物。
3. 查重决策：先看目标 skills 目录，能力相同则更新，能力不同则新建。
4. 写入 skill：`SKILL.md` 保持短小，描述必须包含 `Use when ...`。
5. 校验：行数小于 100 行优先；确认路径、frontmatter、触发词、检查清单完整。

## Workflow

### 1. 定位会话历史

- 当前目录会话：用 `find . -maxdepth 1 -type f -printf '%T@ %f\n' | sort -nr` 找新旧顺序。
- “第二新的”按文件修改时间排序取第 2 个，不按文件名时间猜测。
- `.jsonl` 先用脚本抽取 `user/assistant` 消息和工具调用摘要，避免整文件读爆上下文。
- 如果材料不足，再读取关键行或生成精简摘要。

### 2. 提炼工作流与教训

重点抽取：

- 触发场景：用户用了哪些关键词或任务形态。
- 成功路径：哪些步骤让问题从模糊变清晰。
- 证据纪律：哪些结论来自实测、日志、代码，哪些只是推断。
- 子代理边界：哪些任务适合并行委派，主线程保留什么职责。
- 交付标准：最后的产物如何让别人可直接接手。
- 反模式：中断、误判、重复搜索、过早下结论、未区分主因和次因。

### 3. 更新还是新建

- 若现有 skill 的触发场景和流程相同：更新它的 workflow 或 lessons。
- 若只是从会话中发现新的领域能力：新建独立 skill，避免把无关内容塞进已有 skill。
- 新 skill 目录名使用短横线、语义清晰，例如 `endpoint-performance-diagnosis`。
- 询问用户希望存放skill的位置。

### 4. 写 Skill

`SKILL.md` 推荐结构：

```md
---
name: skill-name
description: <第三人称能力说明>。Use when <具体触发词和场景>。
---

# Skill Name

## Quick start
<最小可执行流程>

## Workflow
<分阶段步骤>

## Lessons learned
<可复用教训>
```

要求：

- description 是触发入口，必须具体，避免“帮助处理文档”这类泛描述。
- 主文件优先控制在 100 行内；超出时拆 `REFERENCE.md` 或 `EXAMPLES.md`。
- 保持一层引用，不在 skill 里嵌入大量一次性会话细节。
- 中文面向用户；代码、命令、文件名保持英文。

## Lessons learned

- “根据当前会话”通常不需要再读历史文件，但要结合当前已完成动作和用户的新意图。
- 创建前必须查重；否则容易把同一能力重复沉淀成多个 skill。
- 会话里的具体案例只作为例子，skill 应沉淀通用决策流程。
- 如果用户要求“更新或创建”，优先说明为什么选择更新或新建。
- 只把验证过的流程写成硬规则；未验证经验写成提醒或检查项。
