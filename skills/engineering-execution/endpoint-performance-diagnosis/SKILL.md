# Endpoint Performance Diagnosis

## Quick start

当用户给出慢接口、curl、页面路径或“接口接近 N 秒”时，不要只凭代码猜测。先建立反馈环，再把耗时拆到代理、网关、业务服务和下游依赖。

最小流程：

1. 明确目标：接口 URL、环境、是否包含前端代理前缀、认证 header、期望耗时。
2. 复现：用最小必要 header 重放 curl，记录 `total`、`time_starttransfer`、状态码、响应大小。
3. 分层测量：前端代理 → 网关 → 业务服务直连 → 下游服务接口。
4. 闭合调用链：页面/客户端 API → Controller → Service → Mapper/远程调用 → 返回前补全逻辑。
5. 排序瓶颈：只把有测量或日志证据的项排在前面；静态推断必须标注“未实测”。
6. 输出修复报告：让接手者知道改哪里、为什么改、怎么验收。

## Workflow

### 1. 建立真实反馈环

- 如果用户提供 curl：保留认证、业务 header、查询参数；删除非必要 cookie 和浏览器噪音 header。
- 用 `curl -k -sS -o /tmp/resp.json -w` 输出：`http_code`、`time_connect`、`time_starttransfer`、`time_total`、`size_download`。
- 分别测：
  - 浏览器/前端代理 URL，例如 `/api/...`
  - 网关 URL，去掉前端代理前缀
  - 业务服务直连 URL
- 若三者耗时接近，瓶颈通常在业务服务返回首字节前；若只有前端代理慢，再查代理和 TLS。

### 2. 先分层，再深入

- 区分“接口响应耗时”和“前端拿到响应后的图片下载/渲染耗时”。用户问接口时，不把后置图片下载混入主结论。
- 找出返回前同步步骤：分页 SQL、count SQL、远程用户信息、Redis 统计、文件签名、权限检查、对象转换。
- 对每个下游调用单独构造请求或查日志时间线，尽量得到毫秒级拆分。
- 必要时抓线程栈，但线程栈只作为定位同步等待点的辅助证据。

### 3. 代码链路取证

- 优先用结构化搜索/CodeGraph/LSP 定位 symbol、调用者和实现；已定位文件后再读取相邻代码。
- 对 URL 使用 literal 搜索反查 Controller；对方法名使用结构化工具。
- 关注伪批量：方法名含 `batch/list/map` 不代表真正批量，必须读实现是否循环逐条 DB/远程调用。
- 检查跨服务 header/权限常量：区分 header 名和值，例如 `from-source` 与 `inner`；这类错误可能既造成正确性问题，也放大耗时。

### 4. 使用 subagent 的边界

- 用户要求并行或存在独立数据流时，立即派 subagent 分析互不重叠的链路。
- 给每个 subagent 明确：只读、关注路径、输出调用链/耗时点/文件行号/是否影响同一瓶颈。
- 主线程继续做复现和分层测量，不重复子代理的页面细节搜索。
- 汇总时交叉验证 subagent 结论；未返回时说明等待/超时，不把未验证内容当事实。

## Repair-ready report template

```md
# 修复报告：<接口>

## 结论
<一句话说明主因，明确不在什么地方。>

## 实测拆分
| 链路 | 耗时 | 证据 |
|---|---:|---|
| 业务服务直连 |  | curl time_starttransfer/time_total |
| 网关 |  |  |
| 前端代理 |  |  |
| 下游 A |  |  |

## 关键调用链
<页面/API/Controller/Service/Mapper/远程服务，附文件路径和行号。>

## 根因
1. <性能主因：例如伪批量、N+1、串行远程调用、慢 SQL、远端 Redis。>
2. <正确性或权限问题：说明是否是主因，是否会放大耗时。>

## 建议修复顺序
1. <低风险正确性修复。>
2. <减少同步远程调用或跳过不必要步骤。>
3. <真正批量化/加索引/缓存/异步化。>

## 验收标准
- 同一 curl 连续多次 `time_total` 降到 <X> ms。
- 下游调用次数从 <N> 降到 <M>。
- 日志不再出现相关权限/失败 warning。
- 相关接口测试、构建或 LSP 诊断通过。
```

## Lessons learned

- 先测 TTFB，再谈前端；TTFB 接近总耗时说明服务器返回前卡住。
- 代理、网关、服务直连的对照能快速排除错误层级。
- “批量接口”最容易隐藏串行循环和 N+1 查询。
- header 常量传错常见且隐蔽：传了 header 名不等于传了内部调用值。
- 性能主因和正确性缺陷要分开写；不要把次要 bug 夸大成唯一瓶颈。
- 只读分析不能声称“已验证修复”，只能说明复现和证据来源。
